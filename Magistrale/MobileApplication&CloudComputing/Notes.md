# Basic Interaction Patterns
Software is made of several components, which interact among themeselves by synchronous or asynchronous pattens. Interactions patterns are:
- Request / Response -> RESTful APIs
	- Most common pattern, synchronous
- One-Way Message (Fire and Forget)
	- Asynchronous message without waiting for response (Log sending)
- Publish Subscribe -> MQTT
	- Publisher sends events to broker on specific topis, and Subscribers receive notifications without knowledge of publisher, broker will be the "postman"
- Event Notifications
	- Passive components that reacts only to events, it's the foundation of event-driven programming. It's the case of visual components, clicking is an event.
	- An Activity is a fundamental software component in any Android application that reacts to events, either generated by the Android framework or by other components. Each Activity responds to a set of predefined events (inherited from its base class) by implementing callback methods (onCreate(),onResume()...).
# Cloud Computing
>Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction. This cloud model is composed of five essential characteristics, three service models, and four deployment models.
>- NIST

We have various cloud deployment: **Public, Private, Community (more than one infrastructure) and Hybrid (mix of public and private)**. Cloud is a different concept than data centers, but in ones there may be deployements of one or more cloud services.

Service models are **Saas, Paas, Iaas, VNFaaS**, all of them providing different layers of utilization to the user.
### Example: Amazon AWS
We have different servcices:
- **EC2 - Elastic Cloud Computing**: Allows quick provisioning of size-variable VMs (IaaS)
- **S3 - Simple Storage Service**: Ensures scalability, data availability, security of data (PaaS) 

### Policies
Cloud policies rely on a tuple of three elements <who, what, how>
- the **who** can be A user, a group or a role
- the **what** is the specific resource, or a pool of them 
- the **how** is the kind of permission needed (read, write, execute, delete...)
## Beyond the Cloud
Cloud services are hosted inside of datacenters, which are beyond the scope of the IaaS. A cloud provider must account for electricity, fire protection, storage, cooling, and security, one thing that the cloud user doesn't need to.
In general the computers inside of a datacenters are mounted inside a Rack, or Blade, in which everything is measured in Us which are units (usually from 1U to 4U each). Servers used for DC are thought for 24/7 operations, and should be used at their full capacity - in fact, a datacenter is usually a quite loud place to be.
### Networking
The traffic is not confined within servers of the same rack; rather, it can be directed to other racks (east–west traffic) or outside the DC (north–south traffic).
In general, in the cloud terminology we have:
- **Availability Zones (AZ)**: name used to denote single/group of physically separate data centers close to each other 
- **Regions**: Aggregations that AZ are in. Example: europe-west2
## Virtualization
A huge tool to provide multi-tenancy along with security, and also with overcommitment
- **Type 0 hypervisors** - Hardware-based solutions that provide support for virtual machine creation byHW partition. They do not manage VM, e.g. do not allow migration, rather partition and HW allocation to OS
	- IBM LPARs and Oracle LDOMs are examples
	- Used on mainframe or high-end servers
- **Type 1 hypervisors** - Operating-system-like software built to provide virtualization Including VMware ESX, Citrix XenServer, Nitro Hypervisor (by ASW plus custom HW cards) Type 1 hypervisors – Also includes general-purpose operating systems that provide standard functions as well as VMM functions (e.g. as kernel module) Including Microsoft Windows Server with HyperV and RedHat Linux - KVM
- **Type 2 hypervisors** - Applications that run on standard operating systems but provide VMM features to guest operating systems Including VMware Workstation and Fusion, Parallels Desktop, and Oracle VirtualBox
## Containerization
Alternative to a full-on virtualization, way less overhead
# Google Cloud Platform
Google Cloud Plaform (afterwards called GCP) is a set of distributed Data Centers of Google. Divided in geographic _locations_ and then subdivided into 40 _regions_ (A geographical region within the world (typically a city) in which at least 3 physical or logical data centers located in different zone) and 121 *zones*. (A logical or physical data center in which cloud resources physically resides).

A location have multiple regions registered, and each region may have multiple zones.
## Resources
Whenever we use GCP we use **resources** which are any component that is configured or managed within gcp. (like cpus, gpus, hard drives, or VMs). Resources can be Global, Regional and Zonal depending on who other can access its resources.
## Projects
Any google cloud resource must belong to a project, which is composed of:
- Project name
- Project ID: string identifier
- Project number (internal identifier)

## Identity and Access Management
With IAMs we have different parts:
- **Resources**: projects, buckets, VM, repos...
- **Member**: individual user account, groups, domain, service accounts, public
- **Permission**: defines what actions can be performed on a resource
- **Role**: collection of permissions. Can be basic roles (owner, editor, viewer), predefined by GCP (Cloud admin, Policy admin, reader...) or custom
- **Policy**: an association of member-role-resource

It's the command line interface with which someone can manage its GCP. It can be provided both in web (via browser) or in a SDK form (locally installable).

# Android Framework
Android is based on the Linux kernel, modified to fit the needs of mobile applications, which some of the key modifications including:
- **Memory Management**: Low memory killer kills apps when resources are low, ensuring responsiveness of the system. Ashmem is a shared memory subsystem for IPC
- **CPU Management**: Wake Locks, which is a way to prevent the cpu from going into sleep mode
- **Communication**: Binder is a better IPC that enables efficient and secure ones, implement the Intent mechanism
## Applications
Android applications are made of different components:
- **Activity**: the foreground service which provides the User-interface
- **Service**: performs the background services
- **BroadcastReceiver**: It's the handler for the broadcast messages from system and other apps
- **ContentProvider**: Manages shared access to app data
These components are completely managed by the Android OS, and are declared in the `AndroidManifest.xml` file. The **Intents** are the way that different components communicate with each other.
## Android Software Stack
It's comprised of different layers, and it's pretty complicated:
### Android Apps
It's any application that a user installs via sideloading or any other means. It resides in the `/data/app` partition, which is rw. It lives in a sandbox, which is totally isolated from any other apps if not for well-determined API calls (permission/intents). It can be uninstallable at will by the user.
### Privileged Apps
They reside in a different folder `/system/priv-app` and have special permission attributes to modify the system. User cannot uninstall them.
### Device Manufacturer Apps
They are all of the applications (which can be privileged or not) that the device manufacturer installs by default on the system.
### Android Framework
Contains all of the APIs, which are:
- **Android API**: All of the Public APIs which are user-accessible as in a SDK.
- **System API**: APIs available only to OEMs and the system apps.
Along with several managers. 
Any android phone has the Java API framework installed, and applications based on this don't include them in their APKs. Nowadays, applications are based on `androidx.*` and `kotlin.*` and implement the API directly in the APK, not having a DLL-like experience.
### Android Runtime
ART is a VM responsible of translating the app bytecode to specific processor instruction. ART uses nowadays the Just-in-time compilation, which compiles the applications bytecode into machine code at runtime for better installation performance, but can become problematic since JIT compiler cannot be run in a no-executable-data environment. Ahead-of-time compilation compiles code into machine bytecode at compiling/installation time, which leads to faster startup time and more predictable performance.

Nowadays android uses JIT compilation, while some forks of it such as GrapheneOS use AOT compilation for better security.
### Hardware Abstraction Layer
The Hardware Abstraction Layer (HAL) in Android is a programming layer that allows the operating system to communicate with hardware components without needing to know the specifics of the hardware. It provides a consistent interface for software applications to interact with various hardware devices, making it easier for developers to create applications that work across different hardware configurations.

## Software architecture
we have 3 different layers, which should be kept separate
- **Presentation Layer**: Responsible for what the user sees, displaying information and handling user interaction: this uses the Activity Component
- **Business Logic Layer** COntains the core logic of the application, processing data, making decisions. Uses Service and Broadcast receiver components
- **Data Access Layer**: handles the interaction between data sources like database, files or external services. Uses the Content provider components
Modern app developemtn are based on the **Model-View-ViewModel (MVVM)** logic, where:
- **View** is the presentation layer
- **ViewModel** is the business logic layer
- **Model** is the data access layer
### UDF
The idea behind the Unidirectional Data Flow is that we have separation between data and events (which are what modifies the data). Event come from the presentation layer and go from that all down to the data access layer, while data flows in reverse.
### Modern App Development
Modern app development works by dividing the application in 3 parts:
- **UI Layer**: displays application data on the screen
- **Domain Layer**: an *optional* layer that sits between the UI and data layer, encapsulates **complex** business logic.
- **Data Layer**: Contains simple business logic of the app and exposes application data
### Design Principles
- **Separation of concerns**. Split the code in separate focused sections for example, UI-based classes should only contain logic that handles UI and operating system interactions and not business logic.
- **Drive UI from data models.** Data models represent the data of an app and are independent from the UI elements and other components in your app. They they are not tied to the UI and app component lifecycle but will still be destroyed when the OS decides to remove the app's process from memory.
- **Single source of truth.** assign a Single Source of Truth (SSOT) to data. The SSOT is the owner of that data, and only the SSOT can modify or mutate it. To achieve this, the SSOT exposes the data using an immutable type, and to modify the data, the SSOT exposes functions or receive events that other types can call.
- **Unidirectional Data Flow (UDF) pattern**. In UDF, a state (data values) flows in only one direction (from the SSOT to the UI element). The events that modify the data flow in the opposite direction.

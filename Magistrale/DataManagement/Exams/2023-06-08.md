**Problem 1**
> Let R(A,B,C) (with 26.000 pages) and Q(D,E,F) (with 10.000 pages) be two relations stored in a heap at processor P0. We know that 200 free buffer frames are available at P0 and that 100 tuples of each relation fit in one page. Also, we know that attribute C of R contains 500 values uniformly distributed in the tuples of the relation, and the same holds for attribute D of Q. Finally, we know that there are 10 processors P1, . . . , P10 that we can use for processing queries, each with 80 free frames available. Consider the query that computes the equi-join between R and Q on the condition C = D, and compare the following two cases:
> 1.1 The query is executed at processor P0.
> 1.2 The query is executed in parallel after sending the tuples of the two relations to processors P1, . . . , P10.
> For each of the above cases, illustrate the algorithm you would use and discuss its cost in terms of number of page accesses (case 1.1) and elapsed time (case 1.2)

Case 1.1:
We know that, given $V(R,C) = V(Q,D) = 500$, we know that there are approximately $52$ pages with the same values for C and $20$ for D.
Considering that $B(R)+B(Q) \le M(M-1)$ we can do a 2-pass joining algorithm, choosing between sort-merge join and simple join. We'll first evaluate sort-merge. Considering that we need $\frac{B(R)+B(Q)}{M} = 180$ pages to hold the sublists, $\min(20, 52)$ to  hold the pages with the same joining value and $1$ for output, $180+20+1 > M$ and so sort-merge is not possible. This means that simple-join will cost $5(B(R)+B(Q)) = 180.000$ page accesses

Case 1.2
Considering that we have 10 processors, we can use a hash function over R.C and Q.D so that no 2 buckets will have the same value. We'll use 10 frames to store the buckets and send bucket $i$ to the processor $P_i$.

Each processor will have $B(R)+B(Q)/ |P| = 3.600$ pages, which is enough for, again, a 2-pass join. Given that each each processor will still have the same number of pages containing the same value for a given y, we will have $3600/80 = 45$ pages for the sublists, $80-1-45 \le \min(52,20)$ and so a sort-merge join is possible.
This means that the overall cost will be $B(R)+B(Q)$ -for loading the pages and sending them to all processors- $+ \frac2{|P|}( B(R) + B(Q)$ -to do the sort-merge, considering that the sent pages are already in buffer. $36.000+ 7.200 = 43.200$

**Problem 3**
> Answer the following two questions, providing a suitable motivation for each answer.
> 3.1: Give an example of three transactions, which obey 2PL and have the following properties: (i) there exists a schedule S on the three transactions such that when S is given in input to a 2PL scheduler, a deadlock occurs; (ii) for each pair of the three transactions and for any schedule S on such pair, no deadlock occurs when S is given in input to a 2PL scheduler.
> 3.2: Try to generalize the above example to the case of n transactions. More precisely, try to come up with an example of n transactions, which obey 2PL and have the following properties: (i) There exists a schedule S on the n transactions such that when S is given in input to a 2PL scheduler, a deadlock occurs. (ii) For each n − 1 transactions of the n chosen transactions and for any schedule S on such n − 1 transactions, no deadlock occurs when S is given in input to a 2PL scheduler

3.1: Given the transactions T1: w1(X) w1(Y), T2: w2(Y) w2(Z), T3: w3(Z) w3(X) we can create a schedule S: w1(X) w2(Y) w3(Z) w1(Y) w2(Z) w3(X) which will create a deadlock (T1 waits for T2, T2 waits for T3, T3 waits for T1). Given the fact that we have this "circularity" on it, any schedule created by any two pair of transactions will work
3.2: The generalization works on this principle. Given n transactions, every one will be of the form $T_i = w_i(x_i)\ w_i(x_{(i+1)\mod n})$, and the resulting schedule will be interleaved as before. $S: w_1(x_1)\ ...\ w_n(x_n)\ w_1(x_2)\ ...\ w_n(x_1)$ 

**Problem 4**
> Let Person(id,age) be a relation with 500 pages stored in a file sorted on ⟨id,age⟩, City(name,region) a relation with 200 pages sorted on ⟨name,region⟩ and Visited(id,age,name,region) a relation with 20.000 pages sorted on ⟨id,age,name,region⟩. With the goal of knowing, for each person, the cities that (s)he has not visited, we want to compute the set difference between the cartesian product of Person and City and the relation Visited. Tell which is the best algorithm that a query engine with 206 free buffer frames should use for this task, indicating also the cost of executing such algorithm.

Given the fact that the relation City can be completely put in memory, we have space for a 1-pass algorithm.
1. We load the entire relation City in memory.
2. We load the first page of Visited
3. For each page of Person:
	1. For each tuple of Person compute the cartesian product on the tuples of city, removing it from the Person buffer
	2. If the computed tuple is in Visited (if it exist at all it will be loaded in memory) then we will ignore the tuple, not putting it in the output buffer and removing it from the Visited frame.
	3. Else put it in the output buffer
4. Whenever a page of Visited or Person gets emtpied, put next page

This has cost $B(Person) + B(City)+ B(Visited) = 20.700$

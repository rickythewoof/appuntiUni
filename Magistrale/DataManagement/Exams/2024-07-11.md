**Problem 1**
>We refer to a setting with both shared and exclusive locks. A transaction T is called cautious if all its lock requests appear before every other action of T. A schedule is called cautious if it is legal and all its transactions are both well-formed and cautious. A lock-based, active scheduler with both shared and exclusive locks is called heedful if it behaves like a 2PL scheduler with the only addition that it does not accept schedules that are not cautious (where we adopt the usual definition of an active 2PL scheduler “accepting” a schedule). Prove or disprove the following sentences.
>1.1 Every cautious schedule is a 2PL schedule.
>1.2 Every cautious schedule is conflict serializable.
>1.3 Every heedful sheduler can avoid to deal with deadlock management.

1. A cautious schedule is a 2PL schedule. In fact, a cautious schedule is both legal and with each transactions being well-formed. Given that all locks requests need to appear before any actions of transaction T, all locks are before all unlocks, and for this reason, the schedule is also a 2PL schedule
2. Given that all cautious schedules are 2PL, and that every 2PL scheduler is conflict serializable, all cautious schedules are conflict-serializable
3. It is, since deadlocks occur because of a particular set of elements are requested by two or more transactions, and those same elements are already locked by someone else. Given this, we know it's not possible to have deadlocks because each transaction, at it's start, will ask for all possible locks for elements that it will need. It can go in two different ways:
	1. The transaction Ti requesting locks is the first to acquire a lock over the generic  set of "deadlocking" elements X, and so it will continue running until it's finished, knowing that even if there is another transaction Tj starting asking for even parts of the same X, then Tj will be paused.
	2. The transaction Ti requests a lock over an element X already locked by another transaction Tj. In this case then the transaction won't start until Tj unlocks it.

**Problem 3**

> select A, count(\*) from R group by A having count(\*) > 10
> 3.1 Illustrate in detail a multi-pass algorithm to solve the problem, and tell which is its cost.
> 3.2 Tell whether the block-nested loop technique is suitable for answering the query.
> 	3.2.1 If the answer is positive, then illustrate the algorithm and tell which is its cost.
> 	3.2.2 If the answer is negative, consider the following question: can we build and use an index during the application of the block-nested loop algorithm in such a way that the modified block-nested loop algorithm is able to produce the result of the query? If the answer to the question is negative, then motivate the answer in detail; if the answer is positive, rovide a detailed description of the new algorithm and tell which is its cost.

1. For the Multipass we can do as follows
	1. Load M pages of A and compute the selection over it. This means that after the selection we will have 30 tuples per page -> 34 pages occupied with the selection of A, which completely fit in the buffer.

	3. For each tuple, if the relative count is less than 10 discard it, otherwise copy the attribute + count in the output buffer, and ignore all tuples referring to that attribute value. (we can separate the already copied attributes over A by writing a special number on the count part)
	4. This has cost $B(R)$

**Problem 4**
> We refer to a setting where the data manager has 3 buffer frames available, we have a table R(A,B,C,D) with 4.000 tuples stored in a heap with 200 pages and we want to compute the relation obtained from R by eliminating duplicates. 
> 4.1 Illustrate in detail a multipass algorithm for solving the problem in the above mentioned setting and tell which is its cost.
> 4.2 Making use of a hash-based index, design an index-based algorithm for solving the problem in the above mentioned setting, provide a detailed description of such algorithm and tell which is its cost.
> 4.3 Making use of a B+ tree-based index, design an index-based algorithm for solving the problem in the above mentioned setting, provide a detailed description of such algorithm and tell which is its cost.

1. just a simple multi-pass based algorithm is sufficient, considering that we will need $K = \log_2 (B(R)/3) + 1 = 8$ passes, the cost of doing duplicate elimination is $(2K-1)B(R) = 3000$ page accesses. Algorithm would work by:
	1. doing K-1 passes to merge the relation R into  $\le 3$ sublists
	2. using the last pass to load the sublists, copying the first-ordered tuple and ignoring the other ones
2. Using a hash-based index algorithm means to create a hash-index. 
	1. For each tuple of T check if it exists in the tuple.
	2. If it doesn't exist then add it to the index, and to the output buffer
	3. If it already exist then ignore it
	4. Cost is $B(R) + 4000 = 4.200$ page accesses.
3. We can setup a ISAM-based index:
	1. Each index entry has 5 attributes, and so each page entry will have 16 children -> fanout is 16
	2. In the worst case, all tuples are unique, and so we will have 4.000 data entries fit in 4000/16 = 250 leaves
	3. Height of the tree is $\log_{16} 250 = 2$
	4. We then scan all data entries
	5. Cost is $B(R) + 2*4000 = 8200$

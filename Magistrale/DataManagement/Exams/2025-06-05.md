**Problem 3**
> Consider the relations S(A,**B**) and R(**B**,C,D,E), where (i) both have **B** as key, (ii) S is stored in a heap with 60 pages (each page with 40 tuples) with an associated hash index whose search key is B, (iii) R is stored in a heap with 900 pages (each page with 20 tuples) and (iv) the buffer has 32 frames available. If your goal is to compute the natural join (equi-join on B) between R and S as efficiently as possible in terms of number of page accesses, which algorithm would you choose among:
> 3.1 block-nested loop,
> 3.2 multi-pass based on sorting,
> 3.3 index-based.
> Explain your answer in detail so as to convince that you choice is the right one

We can try and see cost with all of the methods:
1. For block-nested loop we can compute the join, with S or R as outer block, since we are computing the equi-join on keys, that are unique. Cost will be $B(S) + (\lceil B(S)/M \rceil* B(R)) = 1.860$ pages
2. For a multi-pass algorithm based on sorting we first need to check how many passes we need. $K = \log_{M-1} (B(R) + B(S))$ = 2. Using a two-pass based algorithm we have that the cost is $(2K-1)(B(R)+ B(S)) = 3*960 = 2.880$ pages - which is already more than the block-nested loop
3. Considering we have a hash-index on S, we know that accessing the relative data index has cost 1. We load pages of R, and for each tuple we access the index. Cost is $B(R) + 20*B(R)  = 900+18.000 = 18.900$ pages, which is the worst overall
I would use a block-nested loop because of the fact that it can be applied, and that it has the least number of page accesses

**Problem 4**
> Consider the relation MEETING(**code**,topic,venue,city,date), with 800.000 tuples stored in a sorted file with search key code (which is also the key of the relation), and with an associated sorted index with search key venue. We know that no more than 300 meetings are held in the same venue, that every attribute and pointer in our system occupies 10 Bytes, and that the size of each page in our system is 1.000 Bytes. Consider the following operations 
> (1) given a venue, compute the code of all meetings held in that venue, together with the corresponding topic; 
> (2) insert a new meeting. 
> For each of the two operations, tell which is the worst-case cost of its execution in terms of number of page accesses

We will first calculate some values: Given size of page in bytes is 1.000, and each attribute consumes 10, then we will have 100 attributes/page. Considering that MEETING has 5 attributes, this means that $B(MEETING) = \frac{\#\text{tuples}}{100/5} = 800.000/20 = 40.000$ pages.

The sorted index is unclustered, and this means that it's dense. We know that we need to sort 800.000 index entries, each entry weighing 20 bytes, so we will have that the number of pages of the index is 
$B(INDEX) = 800.000/50 = 16.000$ pages. 

We also know that for every value of venue, we will have no more than 300 tuples with the same attributes, and so the number of index pages with the same value for venue is $\lceil 300/50 \rceil = 6$ 

$V(MEETING, venue) = 800.000/300 = 2.667$ 

We can now compute the costs.
1. Using the sorted index we can compute the cost via: $\log_2 B(INDEX) + 6$ to access all data indexes relative to venue, and then $300$ to access all pages, which at worst will be different each time. Total cost is $321$. This equates to the query:
```sql
	   select code
	   from MEETING
	   where venue = x
	   ```
2. The cost of adding a new meeting in the relation, in the worst case, will be $B(MEETING)$, and then, to update the index, will be $B(INDEX)$. So it's $40.000+ 1+16.000+ 1 = 56.002$ page accesses.

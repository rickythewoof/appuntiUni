**Problem 1**
> Consider a schedule S with both shared and exclusive locks, that is legal and is such that each of its transactions enjoys the following properties: (i) it is well-formed, (ii) it has all the lock operations before the commit action, and (iii) it has all the unlock operations after the commit action. 
> 1.1 Provide the definition of view serializable schedule and prove or disprove that S is view serializable.
> 1.2 Provide the definition of strict schedule, and prove or disprove that S is strict.

1. A schedule S is said to be view-serializable if it exist a serial schedule S' such that S is view-equivalent to S'. A schedule is said to be view-equivalent to another schedule if they both share the same READ-FROMS and LAST-WRITE set, over the same set of transactions. This is the definition of strong strict 2PL schedule, since that all transactions will be keeping a lock on all their elements until they commit. A 2PL schedule is conflict-serializable, therefore also view-serializable
2. A schedule is called strict if every transaction reads-from and writes-to transactions that have already committed. Given that this is a strong-strict 2PL schedule, it means that by definition is strict.

**Problem 2**
> Consider a system with processors P0, P1, . . . , P10, where (i) P0 has 10 buffer frames and stores the relation Exam(student,course,mark) with 1.000 pages, (ii) each of the processors P1, . . . , P5 have 100 buffer frames, and (iii) each of the processors P6, . . . , P10 have 20 buffer frames. Consider the query 
```sql
select student,avg(mark)
from Exam
group by student
```
> and answer the following questions:
> 2.1 Which algorithm would you use for computing the result of the query if you could use only processor P0, and which is the cost of such algorithm in terms of number of page accesses?
> 2.2 Which algorithm would you use for computing the result of the query if you could use processors P1, . . . , P10 for a parallel execution, and which is the cost of such algorithm in terms of both number of page accesses and elapsed time?

1. The query is doing a grouping action. Given that $P_0$ has $M_0 = 10$ we have 2 possible algorithms to go with:
	- Block-nested loop: Can't be done
	- Multi-pass algorithm based on sorting: This needs to have  $K=\log_{M-1} B(Exam) = 4$  passes. The algorithm would work by:
		1. Do the first pass to create M sublists for Exam, sorted on student
		2. Do another K-1 passes such that $B(Exam) \le M(M-1)^{K-1}$
		3. use M-1 frames for the sublists of Exam, and find the smallest tuple t of student
		4. Update the corresponding output tuple until t finishes
		5. This has cost $(2K-1)B(Exam) = 7.000$ pages
2. Considering we are grouping together we would use a good hashing function over student such that no two different buckets have the same attribute student.
	1. Once loaded in $P_0$'s buffer we send the buckets each (considering that we are using a good hashing function each bucket is approximately the same size).
	2. We will calculate the elapsed time in terms of number of page accesses on the more limited group of processors (let's say $P_6$)
	3. Now, $P_6$ will have $B(Exam)/10 = 100$ pages to deal with, and as before will use a multi-pass algorithm. $K = log_{M_6-1} B(Exam) / 10 = 2$.
	4. Without explaining how the algoirthm work, since it's the same as before, and without counting the elapsed time to ship back the result, we know that the elapsed time will be $B(Exam) + \frac2{10}B(Exam) = 1.200$, which is a speedup of around 4x 

**Problem 3**
> Consider the relations R(A,B) and S(**C**,D,E), where (i) both relations are stored in a heap with 9.000 and 30.000 pages, respectively, (ii) the values appearing in the attribute A are the integers between 1 and 100 and such values are uniformly distributed over the tuples of R, (iii) C is the primary key of S. Knowing that the buffer has 200 frames, illustrate the algorithm you would use to answer the query 
```sql
select A,E
from R join S on R.B = S.C
where A > 50
order by E
```
> and tell which is its cost in terms of number of page accesses

$M = 200$
$V(R, A) = 100 \rightarrow V(R,B) = B(R)/V(R,A) = 900$.
Before starting, we can see how the order requested is different from the joining parameters. We can proceed in two different ways:
- 2-pass based simple-join on sort -to assume the worst-:
	1. $B(R) + B(S) = 39.000 \le 39.800 = M(M-1)$ so we can do it in two passes
	2. Apply the selection and the projection on R and S, respectively, and copy the remaining $B(R)/2 + 2/3B(S) = 24.500$ pages, totalling $123$ sublists of $M$ blocks each.
	3. Load each page of the 123 sublists into memory and compute the join with the other $200-123 = 77$ pages.
	4. This has cost $B(S) +B(R) + 2(B(R)/2 + 2/3B(S)) =39.000+ 49.000 = 88.000$ page accesses
	5. The join will create 4500 pages, which we can sort in 3 passes.
	6. So the total cost is $101.500$

**Problem 4**
> Consider the relation PRODUCT(**code**,category,supplier,cost) that stores information about products sold by an e-commerce company, with the code, the category, the supplier and the cost of each product. The relation has 3.000.000 tuples, stored in 300.000 pages, and has 10.000 different values in the attribute cost, uniformly distributed in the tuples of the relation. We assume that all fields and pointers have the same length, independently of the attribute and that there is a sparse, clustering B+-tree index on PRODUCT  with search key cost, using alternative 2. 
> Consider the query asking for the code and the category of the products whose cost is in a given range constituted by 10 values, and tell how many page accesses we need for computing the answer to the query.

The query asked is 
```sql
select code, category
from product 
where cost >= x and cost < x+10
```

Given that the index is sparse and clustering, the relation PRODUCT is sorted over the same search key (cost). Given that number of tuples in PRODUCT is 3.000.000 and B(PRODUCT) = 300.000, the number of attributes per page is 40.
Now, let's calculate the cost of searching through the B+ -tree. 
Considering that all attribute and pointers have the same value, that an index page is 75% full and that a leaf is 66% full, we can calculate fan-out and the number of leaves. The fanout, given that we can fit at max 4.000/2 = 2.000 index entries, will be $20 * 0,75 = 15$
Considering we are dealing with a sparse index, we will need to index only the unique values, which are $V(R,A)= 10.000$. All of these values will fit into $V(R,A) / (20*0,67)= 715$  leaves.
This leaves with a searching cost of $\log_{15} 715 = 3$ (Implying the root is already in the buffer).
This though is to get to the data entry of the first range value. We need at most 2 page accesses to get to the first tuple containing the first range, and given that on average 30 pages have the same value of cost \[and we need to access 10 values], the total cost will be 
$log_{15}715  + 2 + 30*10+ 1 = 36$ page accesses
